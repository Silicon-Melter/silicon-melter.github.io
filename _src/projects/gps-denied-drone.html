Autonomous indoor drone without GPS

2025 – 2026 · Python, C++, ROS 2 (Humble, Jazzy), PX4 Autopilot, MAVROS, RTAB-Map, robot_localization, Gazebo, Raspberry Pi 5, Intel RealSense, RPLidar

Outdoors, a drone knows where it is from GPS. Indoors there is no GPS signal, so it has to work out its position from its own sensors. Over two stages I built the software for an indoor drone that flies a route by itself, then builds a 3D map of the room and finds its own position inside that map.

The problem

A flight controller such as PX4 can hold a drone steady on its own, but to fly anywhere useful it needs to know its position. Every indoor sensor has a weak spot. A camera loses track on blank walls or in poor light. A 2D LiDAR measures distances very precisely, but only in one flat slice of the room, so it gets confused when the drone climbs or tilts. The motion sensors (the IMU) react instantly but drift within seconds if used alone. The work in this project is mostly about combining them so that each one covers the others' weak spots.

Stage 1: flying a route in offboard mode

  • Waypoints from a file. The mission is a CSV file of positions in metres. A trajectory generator turns each row into a TrajectorySetpoint message, the standard target message in PX4.
  • Offboard control node. A ROS 2 node in C++ arms the drone, switches PX4 into offboard mode (where targets come from an on-board computer instead of a pilot) and keeps streaming setpoints. PX4 leaves offboard mode if the stream stops, so the node publishes continuously.
  • A direct bridge to PX4. The micro-ROS XRCE-DDS bridge makes PX4's internal topics appear as ordinary ROS 2 topics.
  • Position from optical flow. A small downward camera measures how fast the floor slides past, much like an optical mouse, and PX4's estimator turns that into position.

Stage 2: a 3D map, and position inside it

Optical flow drifts over time, so for the second stage I gave the drone a depth camera and a 2D LiDAR and used SLAM (simultaneous localisation and mapping): the drone builds a map of the room and, at the same time, uses that map to correct its own position. When it recognises a place it has seen before (a loop closure), the accumulated drift is removed from the whole map.

  • Two ways to measure motion. Visual odometry tracks features between RGB-D camera frames. LiDAR odometry matches each laser scan to the previous one (ICP scan matching). Both come from RTAB-Map's odometry nodes.
  • Fusing them. An extended Kalman filter (EKF, from the robot_localization package) combines the sources, each for what it measures best: the LiDAR for heading and horizontal speed, the camera for height, and the IMU for fast turns.
  • Not trusting the LiDAR blindly. I wrote a small gating node that drops a LiDAR reading when the drone is climbing faster than 0.2 m/s, because the flat scan then sweeps different parts of the walls, or when the LiDAR's position disagrees with the filter by more than 4 standard deviations (a Mahalanobis distance test), which usually means the scan matching has slipped.
  • Feeding PX4. The visual odometry is also sent to PX4 through MAVROS as an external position source, with a 2 Hz heartbeat that tells PX4 whether the estimate is still fresh, so the flight controller can stop trusting it if the camera drops out. On the Raspberry Pi 5 the visual odometry ran at about 13 Hz. I checked that PX4 really used it with ekf2 status: with no GPS at all, it reported a valid local position.
  • Fixing the flight controller's position. PX4's own estimate, from optical flow, had good height and orientation but badly underestimated horizontal movement. A small node takes PX4's estimate, replaces only its horizontal position and velocity with the visual odometry's, and republishes it for mapping.
  • Map once, then localise. A script replays a recorded flight through RTAB-Map and saves the map as one database file. On later flights RTAB-Map loads that map read-only and only localises the drone in it.
  • Testing. I compared six combinations of odometry sources (camera only, LiDAR only, and several fused versions), tried the mapping with the sensors carried by hand before mounting them on the drone, and ran the same localisation launch files in Gazebo with PX4's simulator before the real drone.

The drone was flown in the Ultra-Wideband (UWB) testbed at Temasek Laboratories, National University of Singapore. UWB radio beacons around the room give a ground-truth position to compare the drone's own estimate against.

How the code is organised

The software is split into three ROS 2 packages, each in its own repository: drone_bringup starts the hardware (camera, LiDAR, MAVROS) and sends odometry to PX4, drone_rtabmap holds the mapping and fusion experiments, and drone_navigation runs localisation in a saved map. Keeping them separate meant I could rework one package, for example try a new fusion setup, without risking the packages that already worked on the drone, and add or drop a package without restructuring the rest.

What I learned

  • Fusing more sensors first made things worse. Each sensor worked well on its own, but the fused estimate wobbled and jumped. The odometry nodes reported almost no uncertainty (a covariance of about 0.001), so when two of them disagreed even slightly, the filter decided one was wrong and threw its data away. What worked was letting each sensor feed only the quantities it measures well, and keeping it out of the rest.
  • A position can be wrong in only some directions. When the drone had clearly travelled a long way, PX4's optical-flow estimate said it had moved only about 0.1 m sideways, while its height and orientation stayed accurate. Instead of discarding it, I kept the parts that were right and replaced the part that was wrong, which became the small node described above.
  • Recording data can break the flight. Recording every topic on the Raspberry Pi slowed the visual odometry sent to PX4 from about 10 Hz to 0–2 Hz, because the SD card could not write that much video fast enough. I switched to recording only the topics the map needs, with compressed images, and building the map on a laptop after the flight.
  • Smooth and correct are different jobs. PX4 needs a position that changes smoothly to fly steadily. Localising in the saved map is more accurate, but it jumps whenever RTAB-Map recognises a place. So the two stay separate: visual odometry goes to the flight controller, and map localisation corrects the drone's position in the map.
  • What I would do differently. My fusion is loosely coupled: each sensor computes its own motion first, and the filter combines the answers. A tightly coupled visual-inertial method such as OpenVINS or VINS-Fusion combines raw camera features with the IMU in one estimator. That should handle fast motion and blank walls better, and it is what I would try next.
