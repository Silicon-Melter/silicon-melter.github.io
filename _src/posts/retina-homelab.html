A small homelab, set up and watched by AI agents

November 2026 · about 6 minutes

RETINA is a student project that helps ambulances through Bangkok traffic: cameras measure queues at junctions, and a planner suggests routes and earlier green lights. It needs a small device next to a street camera that passes the video on to our hub PC. I set that device up on a Raspberry Pi 5 in one day, with most of the work done by AI coding agents. This post is about how that went, and why I think home labs like this have become much easier to run.

What the setup does

There are only three pieces:

  • The camera, a TP-Link VIGI IP camera that streams video over RTSP (the usual protocol for network cameras).
  • The edge device, a Raspberry Pi 5 on Ubuntu 24.04 next to the camera. It runs one program, MediaMTX, in Docker. MediaMTX opens a single connection to the camera and relays it: anyone allowed can read the stream from the Pi, and the camera only ever serves one viewer.
  • The hub, an Ubuntu PC in the lab with an RTX 3060 Ti. It pulls the stream from the Pi, shows it on a dashboard for our team, and runs the vehicle detector that measures lane queues.

The Pi and the hub are joined by Tailscale, a private network that works over the internet. That matters because the Pi may sit behind a 4G connection, where you can't open a port on a router. With Tailscale no ports are opened at all, and the stream can only be read from inside our own network.

Before the Pi, the edge was a laptop with an NVIDIA GPU that also ran an ambulance detector. That detector is still in the code, switched off on the Pi, for the NVIDIA Jetson board that will replace the Pi later.

Two agents and a written brief

The hub PC already had a Claude Code session working in the hub's repository (Claude Code is an AI coding agent that runs commands and edits files in a terminal). When the Pi arrived, I asked that session to write a handoff brief for a second Claude Code session that would run on the Pi itself.

The brief is one Markdown file. It states the goal in one line ("relay the camera to the hub"), lists the facts the new agent can't guess (which other Pi is on the same network and must not be touched, where the hub expects the stream), and then gives the steps in order, each with a check: set the hostname, then check it; install Docker, then run a test container; and so on. At the end it asks for a report with the real output of each check, for me to paste back to the hub's session.

Some steps need a person: anything with sudo, signing in to Tailscale or GitHub, typing the camera's password. The brief marks those [user]. The agent asks me to run them, then checks the result itself. Everything else it did on its own: it wrote the Pi section of the setup guide, changed the Docker setup so the GPU-only detector stays off on the Pi, and committed each working step to the repository.

Two rules in the brief did a lot of quiet work. The camera's password lives only in one file on the Pi, readable only by its owner, and never goes into git, logs or the chat. And no video frame leaves the Pi or the hub, because street video shows faces and number plates, which Thailand's data-protection law (PDPA) covers.

Keeping it running without me

A device next to a street camera loses power now and then. I wanted it to come back by itself, so the setup has a few simple layers, each covering what the one before can't:

  1. Boot. The Pi 5 switches itself on when power returns. Docker, Tailscale, SSH and the clock sync all start at boot.
  2. Restart. The relay container is set to restart unless I stopped it on purpose. If the camera boots slower than the Pi, the relay keeps retrying until the camera answers.
  3. Watchdog. A short shell script runs every 2 minutes from cron. It starts the relay if it isn't running. If the camera stops answering, it looks for the camera by its hardware (MAC) address on the local network, because after a power cut the router may hand the camera a new address. When it finds it, it updates that one setting and restarts the relay. It writes what it did to a log and never prints the password. It also has a dry-run mode, so it can be tested without changing anything.
  4. One health check. On the hub, a script checks every hop in order: the containers, the private network to the Pi, the Pi's stream, the hub's copy of it, whether the hub is showing the real camera or its "offline" placeholder, the live video endpoints, and the hub's own API. Each line prints [ok] or [FAIL] with a hint at where to look.

None of this is clever. That is the point: each layer is a few lines that an agent, or a person, can read in a minute.

Where an agent on standby fits

A health check is only useful if someone runs it and reads the answer. This is the part that has changed the most for me. An AI agent can sit on standby, run the check on a schedule, read the watchdog's log, and when something fails, look at the logs it points to and either fix the simple cases or tell me what it found. The hub's session already has SSH access to the Pi for exactly this kind of check.

What makes that safe is the same thing that made the setup easy: the system is small, every check has a clear pass or fail, and the rules about what the agent may not touch (the password, the video, the other Pi) are written down. A simple setup with a good test is more reliable than ever, because the "someone who runs the test" can now be an agent.

Things that went wrong

  • The lab network. The wired lab router turned out to block Tailscale, GitHub, PyPI, Hugging Face and Docker Hub. The hub went back to Wi-Fi as its main link, with only Tailscale's own traffic routed there on purpose.
  • A Wi-Fi adapter that looked connected but wasn't. The hub's USB Wi-Fi adapter has a power-saving bug that stalls traffic while the link still shows as up. Switching power saving off fixed it. This is exactly the kind of fault a "[ok] / [FAIL]" check catches and a glance at a status icon doesn't.
  • The hostname that reset itself. Ubuntu's cloud-init set the Pi's hostname back at every boot until one config line told it not to.
  • The old video path. Before the relay, the hub converted the stream with ffmpeg into HLS, a web video format. It ran 2 to 4 seconds behind and went blank for about 11 seconds on every network drop (measured on 28 October 2026). The hub now pulls the Pi's stream directly and plays a placeholder while the Pi is offline, so the dashboard never shows a blank screen.

What I learned

Writing the brief was most of the work, and it paid off twice: once when the agent on the Pi followed it, and again now, because the brief, the setup guide and the health check together describe the whole system. A home lab used to need someone who remembered how it was put together. Now the memory is a few files that an agent reads before it touches anything.

The relay is the smallest part of RETINA. The perception, map and planner parts, and the emergency-call app, deserve their own posts.
