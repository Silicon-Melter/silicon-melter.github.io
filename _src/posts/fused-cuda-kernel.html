A fused CUDA kernel made our slowest layer 54× faster

November 2026 · about 8 minutes

Our LiDAR driving model was training about 7× slower than the camera-only version. Before trying to fix it, I wanted to know exactly where the time went. The answer was not where I expected.

The model, in one paragraph

I work on end-to-end autonomous driving: one network that takes in sensor data and outputs the path the car should drive. It learns by imitation, copying an expert driver, and we test it in the CARLA driving simulator. Our starting point is HiP-AD, a camera-only model whose decoder uses a set of queries: learned slots that each look for something, such as a car, a lane line or a point on the planned path. To add LiDAR, each query also looks up the 3D LiDAR features near the points it cares about.

That lookup is the part that turned out to be slow.

Measuring first

On an A100, one training iteration took 10.99 s for the LiDAR model against 1.49 s for the camera-only model at the same batch size. The obvious suspect was the LiDAR backbone, the network that turns the raw point cloud into features. The profiler said otherwise: the backbone took 27 ms per sweep, about 1.4% of the extra time.

The time went into the 3D lookup. Three things multiplied together:

  • Many sample points. Each query point gets several learned 3D offsets, per attention group, read at three feature scales. That came to 159 million sample positions per forward pass. The camera branch reads one projected point per query point instead.
  • No regular grid. Camera features sit on a dense image grid, so reading one is simple address arithmetic. LiDAR features sit at scattered 3D positions, so each sample needs a hash lookup and a check of 16 neighbouring candidates, followed by a weighted sum.
  • Python doing GPU work. The 16 candidates were handled by a Python loop of small PyTorch operations. That launched about 140,000 tiny GPU kernels per iteration, and the GPU spent much of its time waiting for the next instruction. Autograd's backward pass for the gather alone took 56% of profiled GPU time, and memory was so tight that the whole lookup had to be recomputed during the backward pass (gradient checkpointing).

A first round of small fixes helped only a little (12.88 s → 10.99 s per iteration). The number of lookups was fixed by the design, so making each small operation a bit faster could never close a 7× gap.

What we changed

The idea was to make the LiDAR lookup work like the camera lookup: one kernel launch instead of thousands, and direct indexing instead of searching.

  1. A dense cell-to-token table. For each feature scale, build once per frame a table that maps every 3D grid cell to the LiDAR tokens inside it. Finding a sample's neighbours becomes an array read instead of a hash search.
  2. One fused CUDA operation. A single kernel does the neighbour search, the distance weighting and the weighted sum for every sample, and writes the result straight into the query features. A second kernel does the backward pass, using atomic adds to accumulate gradients.
  3. The same maths. The model's behaviour stays exactly the same, which makes the kernel easy to test: it must match the slow PyTorch version.

I led the design and the verification. The CUDA code itself was written with AI coding agents working from an exact specification, and I reviewed every step against tests. We set a gate before writing the backward pass: the fused forward had to be at least 4× faster than the old path on real data, or we would stop and rethink. It came in at 49×.

Testing it

A fast kernel that is subtly wrong is worse than a slow one, because training would quietly learn from bad gradients. So the kernel had to pass 111 GPU tests comparing it with the PyTorch reference, on real LiDAR tokens and on synthetic edge cases. Forward outputs and gradients agree to within 1.5 × 10-6.

Part of the training speed-up comes from memory, not raw speed: the old path only fitted batch size 1 on the 4090, and the fused op fits batch 5. At equal batch size the LiDAR model now costs 1.28–1.34× the camera-only one per step, down from about 7×.

What I learned

  • Measure before you guess. I expected the LiDAR backbone to be the problem. It was 1.4% of the extra time.
  • Count the work, not just the time. Writing out "positions × candidates × scales × layers" showed that small speed-ups could never be enough, and pointed at the design.
  • Memory is speed. Cutting peak memory let the model train at batch 5 instead of 1 on the same GPU, which mattered as much as the kernel itself.
  • Agents need gates and tests they can't argue with. The 4× gate and the 111 reference tests made it safe to let AI agents write the CUDA code: a claim only counted once the numbers were in the log.

The faster model made the rest of the research possible: roughly eight times as many experiments fit in the same GPU time.

Numbers come from our internal profiling and benchmark reports (A100 80 GB and RTX 4090, October 2026). The research code is not public yet.
