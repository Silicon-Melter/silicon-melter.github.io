A job board for six GPUs and a few AI coding agents

November 2026 · about 6 minutes

My research runs on six GPUs spread over five machines, and much of the day-to-day work on them is done by AI coding agents rather than by me typing commands. With several agents able to start jobs, I needed one place that shows what runs where and lets me decide what goes next. This post is about that place: a small job board.

The problem

The hardware is an A100 (80 GB) and two RTX 4090s, sponsored by the AIMS Lab at KMITL, plus the two RTX 3070s in my own PC and an RTX 3060 Ti. Training a driving model, running it through hundreds of test routes in a simulator, converting datasets: each of these keeps a GPU busy for hours.

The work is split between several Claude Code sessions. Each one is an AI coding agent working in its own repository: one writes the model code, one prepares data, one runs evaluations, one keeps the plan. They can start jobs on their own, which is the point, but they can't see each other. Without some shared record, two of them can start jobs on the same GPU, both run out of memory (VRAM, the GPU's own memory), and the night is lost. And a job that died at 2 AM looks just like a job that is still running until somebody checks.

So I wanted four things: one page that shows every job on every machine, a rule that a GPU job waits until I say go when its GPU is busy, a way to talk to the agent behind a job, and nothing extra to host or pay for.

How it works

There are three parts, and none of them is a server I run.

  • A private GitHub repository is the database. Each machine has its own branch with one file, state.json: its temperatures, GPU load and memory, and its jobs. One more branch holds control.json, which is where my decisions go (Go ahead, Wait, messages, which machines are on hold). Every write is a normal git commit, so there is a full history for free.
  • A small sync service runs on each machine. Every 2 minutes, and right after a job changes, it reads the GPU sensors, checks that each job's process is still alive, takes the last line of its log, and pushes the result to that machine's branch. It also passes my decisions and messages on to the agent.
  • The board is one static web page on GitHub Pages. It reads and writes the repository through GitHub's API, signed in with GitHub. It has no backend of its own.

The agents use one command, board-job, to register a job before it starts: which machine, which GPU, roughly how much memory and how many hours. If the GPU is free, the job starts. If it is busy, the job is queued and shows up under Needs your call. CPU and background jobs never wait. When a GPU frees up, the next job in line for it can start on its own.

What I look at

Most of the page answers one question: does anything need me? The counters at the top say how many jobs run, how many wait for my decision, and how many need a look. A job needs a look when its process has gone, when it is stuck, or when it has sent no update for more than two hours. The hottest GPU turns orange from 80 °C and red from 87 °C.

Under each job I can press Go ahead or Wait, send a short message to the agent behind it, or press Bump to ask the machine for fresh readings right away. A small tag shows whether that agent is listening at the moment. If it is, a message reaches it in about 10 seconds. If the agent's session has ended, the board says so, because then nothing I send will get through.

Full training runs on the A100 have their own to-do list in a separate repository. The board shows that list read-only, so I can see the whole picture on one screen.

A few details that mattered

  • Checking often without hitting GitHub's limits. The page checks for changes every 5 seconds. It does this with a single conditional request that asks only whether any board branch moved. When nothing changed, GitHub answers "not modified", which doesn't count against the rate limit. Only the files on branches that moved get downloaded.
  • Two people saving at once. Saving a decision means reading control.json, changing it, and writing it back with the version I read. If someone else saved in between, GitHub refuses the write, and the page reads the file again and retries once.
  • Signing in from a static page. GitHub's sign-in flow needs a secret that can't live in a public page. A tiny relay on Cloudflare's free tier holds that secret and swaps GitHub's sign-in code for a token. The relay stores nothing, and the token can reach only the board's repositories.
  • Old messages, new jobs. Agents reuse job names, so every decision and message carries the start time of the job it was meant for. A "Wait" from yesterday's run doesn't stop today's.

What I learned

The design rule that worked best was that agents never decide on their own when a GPU is shared. They can start anything on a free GPU, but a busy one means "ask". That one rule keeps two jobs off the same GPU, and the agents rarely have to wait, since most of the time something is free.

Using git as the database also worked better than I expected. A board without a server looked like a compromise at first. In practice it means nothing to keep running, every change has a history, and an agent can read the same files the page reads.

The board has since grown a second page, an "agent office", which shows the agent sessions themselves: which ones are active, what helpers they started, and who messaged whom. That one deserves its own post.
